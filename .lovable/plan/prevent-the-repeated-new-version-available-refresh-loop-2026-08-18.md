# Prevent the repeated “new version available” refresh loop

## Verified current state

- The published app currently serves build `31395a` in both the loaded JavaScript and `/version.json`, so the live deployment is synchronized now.
- The prompt is generated by the version checker five seconds after the app loads whenever those two values differ.
- “Refresh now” currently performs only `window.location.reload()`. If an older app shell is still being served from a service worker/browser cache while the version manifest is already current, reloading can reproduce the same mismatch and prompt indefinitely.

## Changes

1. **Add a safe update-refresh helper**
   - Dismiss the update notice.
   - Unregister only SUPERDRIVE’s app-shell service worker and clear only its page/asset caches.
   - Preserve authentication, local application data, IndexedDB, and offline ELD records.
   - Reload once so the browser requests the current app shell directly.

2. **Make the prompt loop-proof**
   - Record which remote build the user already attempted to load.
   - After that reload, do not immediately show the same “Refresh now” action again if the host is still temporarily serving mismatched deployment files.
   - Continue checking quietly; clear the attempted-version marker as soon as the local and remote versions match, so future genuine updates still prompt normally.

3. **Use one update path everywhere**
   - Apply the same helper and loop guard to the automatic version check, the app refresh hook, and the build-status banner so the three entry points cannot behave differently.

4. **Verify the recovery behavior**
   - Add focused tests for first mismatch, successful refresh, repeated same-version mismatch, and a later genuinely new version.
   - Confirm the refresh cleanup does not remove login/session state or offline driver data.

## Immediate recommendation

Do not keep pressing the button. Since the published build is synchronized now, fully close the SUPERDRIVE tab/app and reopen it once; the prompt should no longer return. The implementation above prevents the same experience during future deployments.
