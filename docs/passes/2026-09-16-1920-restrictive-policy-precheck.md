```sql

```

The unique key is on the PAIR, so **two rows for one user are permitted**. The live resolver:

```sql
CREATE OR REPLACE FUNCTION public.current_company_id()
 RETURNS uuid LANGUAGE sql STABLE SECURITY DEFINER SET search_path TO 'public','extensions'
AS $function$
  SELECT COALESCE(
    (SELECT cm.company_id FROM public.company_members cm WHERE cm.user_id = auth.uid() LIMIT 1),
    (SELECT o.company_id  FROM public.operators o       WHERE o.user_id = auth.uid() LIMIT 1),
    (SELECT t.company_id  FROM public.truck_owners t    WHERE t.user_id = auth.uid() LIMIT 1)
  )
$function$
```

`LIMIT 1` with no `ORDER BY`: with two membership rows the answer is an **arbitrary** company,
and it may differ between plans. A restrictive policy would then hide the other carrier's rows
non-deterministically — a screen that works one day and empties the next. Identical for a
truck owner with `truck_owners` rows in two companies, and for a driver with two `operators`
rows. Multi-company users are not supported today; this decision does not make them supported,
it makes the ambiguity load-bearing. Either add a unique constraint on `user_id` alone or make
the resolver deterministic before any user is put in two companies.

### (f) WRITES — trigger ordering, and tables written without a stamp

PostgreSQL 16, *CREATE POLICY* (https://www.postgresql.org/docs/16/sql-createpolicy.html),
verbatim:

> For INSERT, UPDATE, and MERGE statements, WITH CHECK expressions are enforced after BEFORE
> triggers are fired, and before any actual data modifications are made.

> Thus a BEFORE ROW trigger may modify the data to be inserted, affecting the result of the
> security policy check.

Same page, on combination, which is why one restrictive policy is enough:

> All restrictive policies which are applicable to a given query will be combined together
> using the Boolean "AND" operator.

> When a mix of permissive and restrictive policies are present, a record is only accessible
> if at least one of the permissive policies passes, in addition to all the restrictive
> policies.

> If only restrictive policies exist, then no records will be accessible.

That last line matters for two tables: the census found `document_short_links` and
`message_notification_throttle` have **no policies at all**. Adding a restrictive policy there
changes nothing (they are already inaccessible to `authenticated`), but the guard must not
read their emptiness as compliance.

Live `pg_trigger`, tables with `company_id` and NO company-stamp trigger:

```sql

       LEFT JOIN pg_proc p ON p.oid = tg.tgfoid AND p.proname LIKE '%company%'
```

**147 of 148 stamp.** The exception is `company_members` itself, which has no company stamp
because its `company_id` IS the assertion and it is service_role-only (no non-SELECT policy,
no write grant to `authenticated`). Everything else sets `company_id` in a BEFORE trigger
that fires before the WITH CHECK, so writes cannot be broken by the restrictive predicate
unless a trigger is dropped.
