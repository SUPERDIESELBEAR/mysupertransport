## STEP 2 — the grant-parity regression, and why it will recur

**What failed.** `src/test/grant-parity-live.test.ts`, since about 13:35 UTC:
`permission denied for function grant_parity_report`.

**Evidence, from the live catalog (not migration text):**

| Reading | Value |
| --- | --- |
| `pg_proc.proacl` for `grant_parity_report()` | `postgres=X/postgres, service_role=X/postgres, sandbox_exec_qgxpkcudwjmacrdcyvhj=X/postgres` |
| `current_user` / `session_user` in the harness session | `sandbox_exec` / `sandbox_exec` |
| `has_function_privilege('sandbox_exec', …, 'EXECUTE')` | `false` |
| function ACLs anywhere still naming the bare role (`sandbox_exec=`) | **0** |
| `pg_roles` oids | `sandbox_exec` **35560**, `sandbox_exec_qgxpkcudwjmacrdcyvhj` **27530** |
| table ACLs naming the bare role | **221**, all `sandbox_exec=ar/postgres` (e.g. `dispatch_daily_log`) |

So: the harness role name did **not** change — it is the same plain `sandbox_exec` that
migration 0008 granted to on 2026-09-17. The function was **not** recreated: no migration
after 0008 mentions it (`rg grant_parity_report drizzle/migrations` → 0004, 0008 only),
and its owner is still `postgres`. No migration revokes it.

What is left is the role itself. `sandbox_exec` carries the **higher oid of the two**, so
the bare role is newer than the project-suffixed one, and it holds a fresh
`ar` (SELECT/INSERT) grant on 221 public tables that no migration in this repo issued —
sandbox provisioning re-issues those. Dropping a role removes it from every ACL in the
cluster, which is exactly the shape observed: table grants re-created by provisioning,
function grants made by migration gone. The loss of `cron` and `drizzle` schema access in
this session is the same story from the other end.

**Fix, the same way as 0008:** migration
`drizzle/migrations/0019_grant_parity_report_execute_regrant.sql` — EXECUTE granted to
`"sandbox_exec"` and `"sandbox_exec_qgxpkcudwjmacrdcyvhj"`, with the explicit
`REVOKE ALL … FROM PUBLIC / anon / authenticated` kept. The function reads every public
table's grants and must never be client-executable.

**After the fix:** `has_function_privilege(current_user, …)` = `true`,
`select count(*) from public.grant_parity_report()` = **0 offenders**, and the file passes
**3/3**:

```
 ✓ src/test/grant-parity-live.test.ts (3 tests) 3216ms
   ✓ grant_parity_report() exists and is readable from the catalog
   ✓ no public table admits a role its grants do not
   ✓ parser_diagnostics is written only through the definer RPC
```

**Plainly: this fix will not stick.** If sandbox provisioning recreates `sandbox_exec`
again, the grant disappears again and the file goes red again — this is its second
occurrence in four days. What would make it stick is one of:

- provisioning granting the sandbox role EXECUTE on `public` functions the way it already
  grants table `ar` (outside this repo's reach); or
- the harness connecting as the durable project-suffixed role, which already holds
  EXECUTE (a change to the sandbox's `PGUSER`, also outside this repo); or
- the guard calling the report through an RPC as `service_role` instead of psql.

The test was deliberately **not** softened. A missing privilege must stay RED, per the
standing note at the top of that file.

## STEP 3 — the probe rule, tightened

Appended to `docs/tms-build-status.md` as a standing rule, verbatim:

> A probe made through a live PostgREST session, which cannot be rolled back, must be
> built so that an ADMITTED caller lands on a guaranteed failure — a bogus foreign key, an
> invalid enum value, or a check constraint — and never on a successful write. A plain
> write is only permitted inside a transaction that raises.

Cited incidents, all three real rows changed by a probe:

1. **Invoice `ST26-0001`** — a probe write committed to a real invoice row.
2. **Two `ica_review_links` notes** (2026-09-17 2330) — `note = 'tenancy probe control'`
   PATCHed onto two real rows as a positive control; cleared to NULL, original text
   unrecoverable.
3. **2026-09-21 1424** — the reactivation of archived driver `8c0ccadb-…` committed (his
   original `deactivated_at` / reason / actor are unrecoverable), and the ordinary-edit
   arm set `notes` to NULL on `f2051752-…`.
