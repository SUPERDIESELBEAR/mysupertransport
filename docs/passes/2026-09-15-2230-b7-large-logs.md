`notifications` 10,827 · `dispatch_daily_log` 5,890 · `audit_log` 3,991 ·

## What was done

### Migrated

- **`notifications`** — `company_id` NOT NULL, no surviving default, FK
  RESTRICT, own index. Stamped by a new `stamp_company_from_recipient()`
  (SECURITY DEFINER, `search_path = public, extensions`, EXECUTE revoked from
  PUBLIC / anon / authenticated). It derives the company from the RECIPIENT
  (`company_members` -> `operators` -> `truck_owners`) and RAISES 42501 when the
  recipient resolves to nothing. The caller-based resolver is unusable here:
  cron jobs, edge functions and definer paths write most rows with no
  `auth.uid()`.
- **`dispatch_daily_log`** — same shape, reusing the existing parent-derived
  `stamp_company_from_operator()`; `rollover-dispatch-status` writes it as
  service role with no company.

### Stopped, as instructed, rather than guessed

- **`audit_log`** — 1,077 rows underivable (1,021 null `actor_id`; 56 actors
  resolving to no membership / operator / truck owner). Entity types among them:
  operator 446, pei_request 296, application 211, rods_day 63, ica_contract 45,
  accessorial_adjustment 5, dispatch_settlements 3, compliance 3, and one each of
  truck_owner, invoices, settlements, onboard_assignment_sheet,
  truck_dot_inspections.
- **`email_send_log`** — no tenancy key at all. 1,340 rows with null `metadata`;
  the rest partial. Recipient-address joins were attempted and are impossible:
  `profiles.email` and `operators.email` do not exist.

Both stops are asserted in the guard, in both directions: the suite fails if a
`company_id` appears on either table, and fails if the underivable counts reach
zero (at which point the decision should be revisited, not quietly outlived).

## The duplicate unique index

Two byte-identical unique definitions existed on `(operator_id, log_date)`. The
first migration attempt dropped the wrong one and failed verbatim:

```
ERROR: 2BP01: cannot drop index unique_operator_log_date because constraint unique_operator_log_date on table dispatch_daily_log requires it
```

No partial change. The corrected migration dropped the plain
`dispatch_daily_log_op_date_uniq` and kept the constraint-backed
`unique_operator_log_date`, which the `onConflict` upsert paths name.

## Timings — what is and is not claimed

DDL could not be timed: the connected role is not the table owner —
`ERROR: must be owner of table notifications`. Read-only derivation simulations
over the full row sets took ~175 ms (notifications) and ~148 ms (dispatch). That
is not a lock-duration measurement and is not presented as one.

queries return 0. Policies 560 before and after.

An earlier 403 on the staff notification insert was NOT an authorization defect:
`Prefer: return=representation` makes the INSERT return rows, and RETURNING is
subject to the SELECT policy, which scopes notifications to their own recipient.
Without the representation header the same insert is 201. Recorded because the
error text (`new row violates row-level security policy`) reads as an insert
refusal and is not one.
